# Engineering Log Maintenance Skill

All agents, developers, and tools working in `tcmichals/inav` MUST maintain the persistent engineering chronicle in [`docs/ENGINEERING_LOG.md`](../../docs/ENGINEERING_LOG.md).

## 1. When to Add an Entry
An entry is required whenever:
1. An architectural design decision or refactoring occurs (e.g. coroutine execution, memory layout, AbstractX TLP routing).
2. A feature, filter stage, or algorithmic change is ported from upstream INAV or Betaflight.
3. A bug is diagnosed and resolved.
4. Hardware platform bindings change (RP2350 Pico 2 W, Cubie A5E, QMTECH Zynq/FPGA, ESP32-P4).
5. New differential or unit test suites are introduced.

## 2. Standard Entry Format
Append new entries chronologically at the bottom of [`docs/ENGINEERING_LOG.md`](../../docs/ENGINEERING_LOG.md):

```markdown
---

### [YYYY-MM-DD] <Title of Change / Milestone>
- **Category**: `feature` | `bugfix` | `hardware-fact` | `parity` | `refactor`
- **Decision**: Concise 1-2 sentence description of the architectural or algorithmic decision.
- **Rationale**: 
  1. Technical reason for the change, memory impact, or timing constraint.
  2. Hardware trade-offs (e.g. WCET, bus bandwidth, power, DMA vs PIO).
- **Files Modified**: Comma-separated list of changed files with links.
- **Verification Evidence**: Exact test command executed and output metrics (e.g. pass counts, jitter, bit-exact parity).
```

## 3. Mandatory Rules
- **No Unverified Claims**: Only record metrics (cycle counts, test results, bit-exactness) that were directly generated by executing the relevant validation commands in the local working tree.
- **Record Hardware Facts**: When physical sensor constraints or bus behaviors are identified (e.g. oscillator lock times, conversion latencies), document them explicitly.
